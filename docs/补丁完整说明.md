# Tracky Mouse 3.1.0 · 语音控制与校准补丁 v50（语音控制 + 舒适范围校准 + 语音开关 + 限速与验证门 + 语音离合器联动 + 自动回中 + 分阶段回正 + 「静止」只停移动 + 校准增益量纲修复与防抖 + 「闭嘴/闭眼」彻底关掉点击 + 声控按键双音节「左键/右键/中键」+ 点按模式 + 总开关词可单独静音 + 改名「yz的游戏鼠标」+ 常规页改造人署名 + 边缘「隐形墙」修复）

> **v50.1 紧急修正：初版 v50 装上后打不开**——初版 `cursor-clutch.js` 误用了 ES 模块语法，Electron 主进程加载它直接崩溃（`ERR_REQUIRE_ESM`），应用无法启动。已改回 CommonJS 并加了两条防线（主进程补丁模块禁止 ESM 语法），重新解压本包运行 install.ps1 覆盖安装即可，不用卸载。
> **v50：修复「光标到不了最上/最下一行」的隐形墙**——你报告的现象（有时碰到屏幕边界、头部还能动但光标到不了边、只有「静止」再「移动」才能恢复、开始时光标的位置会影响、中心点不在正中间）已定位到主离合器的**缝合偏移只锚定一次**：开启追踪时的回中瞬移是异步的，而解除暂停会立刻开始发送移动事件，于是「脱离」第一帧把锚点定在了**瞬移前的旧位置**，这个差值从此留在映射里——渲染层把自己的坐标钳制在屏幕内，所以实际可达范围整体偏移：**开始时光标越靠边，墙越大、方向就朝哪边**。修复为**每一脱离帧都重新锚定到当前真实光标位置**（原代码只在 toggle 键边缘这么做，且注释里写的设计意图本就是「从光标实际所在处继续」）。修复后：说「静止」停车、说「移动」恢复、按 F9、物理移动鼠标，都不会再产生偏移；「开始」后中心点始终在屏幕正中。详见「v50」一节。
> **v49：软件主体改名为「yz的游戏鼠标」+ 常规页末尾加入改造人署名**——窗口标题、标题栏文字、覆盖层无障碍标题都换成了新名字；设置 → 常规的最后一栏新增两行：「**改造人：yz的人生游戏单**」（点击整行在系统浏览器打开 B 站主页）和「**根据开源项目 tracky-mouse 进行改造**」（点击可访问项目主页）。跳转链接在主进程做了**白名单校验**，渲染层无法要求打开任意网址。详见「v49」一节。
> **v48：「开始」「停止」各自一个开关**——v46 给的是「总开关词」一对一起静音；实际用起来这两个词的性质差很远：**「开始」在日常说话里太常见**（「开始做…」「我先开始」），需要单独掐掉，而**「停止」通常是故意说的**，得留着。所以 v48 把它拆成两行：设置 → 语音控制 → 总开关词方案下方，现在是**「响应「开始」（开启光标移动）」**和**「响应「停止」（停止光标移动）」两个独立勾选**，标签会跟着你选的方案自动换词（选「开启/关闭」方案就显示「开启」「关闭」）。只关一个不影响另一个，两个都关就等于原来的总开关；**「移动 / 静止」「眨眼 / 闭眼」「张嘴 / 闭嘴」和三个声控按键始终不受影响**，改动即时生效、不用重启。旧配置里如果之前把总开关词整对静音了，升级后会自动落成两个都关，不会突然又开始响应。详见「v48」一节。
> **v47：声控按键改成双音节「左键 / 右键 / 中键」——单音节的漏识别彻底解决**——上一版换成「左 / 右 / 中」确实比「一 / 二 / 三」好，但你实测仍觉得 1 号和 2 号不如 3 号灵。这次把三个词放到同一套条件下量了一遍（男女两个 TTS 音色 × 说话前静音 0 / 0.3 / 1 / 2 / 3 / 4 秒 × 每格 5 次，共 60 次一词）：**单音节全都不够稳**——左 42%、中 50%、三 75%、右 67%、后 92%，只有下 / 前 / 上 到 100%；而且失手不是「偶尔差一点」，而是**某个停顿长度下 5 次全不中**，即那个场景下这个词对识别器等于不存在。**换成双音节后是 180/180（100%）**：左键、右键、中键在同样条件下一次不漏，连原来最差的「左」「右」都补上了。因此 v47 把三个默认词改为 **左键 / 右键 / 中键**，已装的旧配置首次启动会**自动升级**（你手动选过的词不会被改），下拉里也只保留稳的词（带 ★ 的是实测最优）。详见「v47」一节。
> **v46：换词 + 「开始/停止」可单独关掉**——①声控按键的词从「一 / 二 / 三」换成**「左 / 右 / 中」**：你反馈「一」「二」不好触发是对的——离线实测（同一词表、同一阈值、两种 TTS 音色）「一」单说几乎不命中（连念三次也只中一次），「三」最好；换成「左 / 右 / 中」后单发命中率提高到 4/6，误触反而更少（负样本 3 个降到 1 个，日常句子 3 个降到 2 个）。②**每路声控按键的词都能自选**（左/右/中/前/后/上/下/点）：实测「右」以 y 起音、起音弱，说话前停顿较久时容易漏——2 号键常不灵时换成「后」或「下」即可。③设置里新增**「响应总开关词」**开关：可以单独关掉「开始」「停止」（或所选方案的那一对词）的识别，其他词完全不受影响。详见「v46」一节。
> **v45 新功能：声控按键点按模式**——实测反馈「一二三不太灵敏，是不是要长按持续念导致的」：对，按住（hold）模式要求拖长音或连续念（「一——」或「一，一，一」），单发一个「一」只按住 0.8 秒，且识别的边缘性让单发短音时灵时不灵。v45 在设置 → 语音控制新增**「点按模式：听到即点击一下，而非按住」**（默认关闭）：开启后**每听到一次关键词就立即短点一下**（按下约 0.1 秒后松开），不需要拖长音也不需要连续念——单个「一」就是一次点击，连念「一，一，一」就是连续多次点击。详见「v45」一节。
> **v44 修复/新功能：声控按键独立通道 + 声控时不再误触张嘴点击 + 感叹号可对声控按键隐藏**——①排查确认：声控按键与张嘴点击在代码里**完全独立**（语音识别→按住窗→分区注入 vs 嘴部手势→离合器→分区注入），实测「张嘴点击关闭 + 声控按键开启」时说「一」照常按下——之前"关掉张嘴点击后声控按键失灵"的观感，来自**两个默认绑定都是左键**：张嘴点击开着时说「一」必然张嘴，是**张嘴手势**在按左键（与声控按键同一个键），关掉后声控按键的识别边缘性（单音节「一」需连续念）就暴露出来了。②真正的问题是**声控时会误触张嘴点击**：v44 起**声控按键按住期间张嘴点击自动被压制**（运行时压制，不写设置），说完松开立即恢复——两条通道无论怎么组合都互不叠加。③设置 → 语音控制新增**「隐藏声控按键的语音确认符号（!）」**（默认隐藏）：声控按键说到就触发、常常连续触发，感叹号会一直闪；开关词（移动/张嘴等）的感叹号不受影响，取消勾选可恢复显示。详见「v44」一节。
> **v43 新功能：声控按键「一 / 二 / 三」——持续发声 = 一直按住一个键**——设置 → 语音控制里新增三个**默认关闭**的「声控按键」开关：说一声 **「一」**（或「二」「三」）就按下你绑定的按键，**只要继续发声（持续念「一……」）按键就一直按住**，停下来约 1 秒自动松开——不用一直张着嘴，比开口点击更省力。每个槽位可绑定**一串按键**（默认鼠标左键，照 v28 张嘴点击按键的录法），三个槽位互不影响、与张嘴/眨眼点击随意组合。实现是两道保险：**每次命中按下（0.8 秒窗）+ 麦克风能量续窗**（声音不断按键不松，换气、拖长音都不怕；最后一次命中后最多再按 4 秒防噪声无限延长）。语音键豁免 3 秒同词冷却（按住 = 连说本来就是预期）。注意：**「一」在中文日常语音里很常见**（「一个」「一起」都带这个音），开启后日常说话可能偶尔误触发按下，所以三个槽位默认全关、要用哪个开哪个。识别仍完全离线。详见「v43」一节。
> **v42 修复：说「闭嘴」/「闭眼」关不掉点击**——软件里其实有**两条点击路径**：旧的「点击模式」下拉（悬停/眨眼/张嘴点击…直接按鼠标键）和 v28 的「张嘴点击 / 眨眼点击」复选框（按绑定的键）。语音词切换的是**复选框**，而复选框一关，软件会**自动退回旧点击模式**——于是说完「闭嘴」，张嘴照样点击（走的已经是另一条路了），「闭眼」同理退回旧「眨眼点击」模式。现在语音说「闭嘴/闭眼」会**把旧路径也一起静音**：说「闭嘴」= 张嘴彻底不点击，说「张嘴」才恢复；**重新开始追踪也会自动复位**。顺手修了一个连说两条指令会被吞的问题：**3 秒冷却现在只对同一个词生效**，「移动」→「闭嘴」可以连着说，第二个词不再被静默丢弃。三个开关从此真正互不影响：**张嘴管张嘴点击、眨眼管眨眼点击、移动管光标移动，随意搭配**。详见「v42」一节。
> **v41 修复：校准完光标上下乱抖**——根因不是参数，是**校准的增益公式量纲错了**：把「记录的位移（占屏幕比例）」和「到角落的距离（像素）」直接相除，算出来的倍数大了几千倍，于是**每次校准四个方向全部被顶到上限 ×12**，等于把摄像头的细微抖动也放大 12 倍——校准一结束光标就开始上下乱跑，验证按钮点不中，校准永远过不去（同一个 bug 还让进度条一直显示 0%）。现在公式带上了屏幕尺寸，实测正常转头给出的是 **×1.4～×2.6**（以前是 12）；旧校准留下的 ×12 会被**自动清回 1**；另加一层防抖兜底（限幅 ×6、上下/左右最多差 2 倍、按增益自动加死区+平滑，可用下拉关掉）；验证阶段改成**从按钮左侧、与按钮同高的位置起步**，只需左右移动，上下抖动不再让校准失败。详见「v41」一节。
> **v40 修复：校准「回正」的顺序 + 更短的回中间隔 + 「静止」不再连点击一起关**——① 校准里点完确认，**光标不再立刻被搬回中心**：先**冻结**在原地等你把头转回来（头怎么动都不影响光标），确认头停稳后才**平滑滑回中心**，落位那一刻才把该姿势当作基准，最后才**张嘴**开始下一方向——「仰着头点完 → 头一回正就把光标推到另一边」这个让校准失败的老问题没了；② 自动回中新增 **0.5 秒 / 1 秒** 两档（默认从 3 秒改为 **2 秒**）；③ 说 **「静止」现在只停光标移动**，相机与点击继续工作——**「静止」→「张嘴」→ 点击** 完全可行（以前「静止」等于按 F9，把点击也一起关了）。详见「v40」一节。
> **v39 新功能：静止自动回中 + 校准每步「回正头部」+ 感叹号可调大小**——①「开启时的光标位置」改名为 **「开启鼠标移动时光标位置」**（软件可以常开，这里只管光标移动开始的那一刻）；②「光标移动」栏新增 **「静止几秒后自动回到中心位置」**（默认 3 秒）：光标连续 N 秒没动就平滑滑回屏幕中心，把长期累积的偏移向量清零——**用着用着偏左/偏右**的老毛病有解了；③校准四步之间插入 **「请回正头部，张嘴确认进行下一个方向」**，每一步都从**屏幕中心**出发测量（以前头没转回来，下一方向就被污染，校准完只能动一小块）；④v38 的黄色感叹号 **可调大小**（大/中/小/特小，默认「中」＝小一号）。详见「v39」一节。
> **v38 新功能：语音指令联动离合器 + 光标旁黄色感叹号回执**——语音开关和离合器现在是**同一个开关**了：说 **「张嘴」** 不再只是勾上复选框，还会**同时接合第二离合器**（不用按离合器键，张嘴点击立刻生效）；「眨眼」联动第三离合器、「移动/开启」等联动主离合器，「闭嘴/静止/关闭」则分离对应的离合器。之后**只要按一下实体离合器键，控制权就交还给按键**。另外，每次语音识别成功，**光标右上角会出现黄色感叹号 1 秒**（软件最小化也能看到，知道刚才那句话生效了）。详见「v38」一节。
> **v37 新功能：限速 + 口头确认 + 10 秒验证门**——上一版校准后「一点抖动就飞天」的问题解决了：新增**最大移动速度**上限（提高灵敏度的同时压住抖动），校准全程改用**张嘴确认**（不用键盘），并把校准按钮**搬到大「开始」按钮旁边**；四步做完后有 **10 秒验证门**：新灵敏度临时生效，必须用头控点中屏幕中央的「调试完成」按钮才算数，**超时自动恢复校准前的状态**——再也不会出现「调完反而没法用还改不回去」。详见「v37」一节。
> **v36 新功能：语音开关 + 内存提醒**——语音控制里那几件事现在都能**用嘴单独开关**：说 **「移动」/「静止」** 开关光标移动，说 **「眨眼」/「闭眼」** 开关**眨眼点击**，说 **「张嘴」/「闭嘴」** 开关**张嘴点击**（三个开关各自可勾选，默认全开）。同时「语音控制」这个大标题后面直接标上了 **（开启后内存消耗增加）**，一眼看到代价。详见「v36」一节。
> **v35 新功能：舒适范围校准**——头转到舒服的极限了，光标却还够不到左上角/右下角？设置 → 光标移动 → **校准舒适范围…**，依次朝**左上、左下、右上、右下**各做一次舒服的转头动作，校准会**分别放大四个方向的灵敏度**，让同样的动作正好走到角落。详见「v35」一节。
> **v34 新功能：语音控制**——打开「语音控制」后，**说一声「开启」光标就开始跟随头部，说「关闭」就停下来**，不用手、不用保持闭眼、也不用去按 F9。识别**完全在本机离线**跑（补丁自带一个约 5 MB 的中文关键词模型，只监听你选的那两个词，听不懂别的），三组词任选：**开启/关闭**、**开始/停止**、**打开/关闭**。详见「v34」一节。

## v50：修复「到不了最上/最下一行」的隐形墙

### 1. 现象与根因

你报告的现象：

- 有时光标到不了最上或最下的一行，**感觉像碰到屏幕边界**，但头部还能动；
- 只有**说「静止」再「移动」**才能恢复；
- **开始（启用）时光标的位置会影响它**，有时中心点不在屏幕正中间。

根因在主离合器（按住/点按控制键才移动光标的那套机制）的「缝合偏移」：

1. 脱离（停车）时，光标冻结，系统记下「头部目标 − 光标位置」的差值，接合时用这个差值把头部坐标接回到光标实际所在处——本意是对的；
2. 但**锚点只在脱离的第一帧捕获一次**。而「开启追踪」时的回中（把光标瞬移到屏幕中心）是**异步**的，解除暂停又会立刻开始发送移动事件——于是第一帧锚定的是**瞬移前的旧位置**，差值变成了「中心 − 旧位置」并永久留在映射里（停车期间物理移动鼠标同理）；
3. 渲染层把自己的坐标钳制在屏幕范围内，主进程却拿「内部坐标 − 差值」直接下屏。差值非零时，**实际可达范围整体偏移**：开始时光标越靠边，墙越大，方向朝着开始时的位置的反方向——到不了最上或最下一行，「中心点」也不在正中间；
4. 「静止 → 移动」之所以有效：静止会持续把渲染层指针钉回真实光标，几帧后差值归零，重新接合就干净了。这也反过来证实了根因。

### 2. 修复

离合器逻辑抽成独立模块 `cursor-clutch.js`，并把锚点改为**每一脱离帧都重定为当前真实光标位置**：

- 停车期间渲染层指针本来就被钉在真实光标上，所以差值恒为 ≈0；
- 任何让真实光标移动的情况——启用回中瞬移、物理移动鼠标——都会在下一帧被自愈，不再积累进映射；
- 重新接合永远「从光标实际所在处继续」——这正是原代码注释里写的设计意图，旧实现违背了它；
- toggle 键边缘原有的「手动清锚点」补丁被逐帧重锚自然取代。

### 3. 验证

- **单元用例 142/142**（新增 N 组 11 项：直通/接合/脱离分支、**启用瞬移场景下重新接合从当前位置继续**、隐形墙属性（从中心扫到底部全程可达）、park 期间偏移收敛、reset、开关切换、主进程接线、旧逻辑移除）。测试里内嵌了**旧算法对照**：同一场景下旧实现确实产生 540px 的映射错位（N4b/N5b），证明修复的必要性。

## v48：「开始」「停止」各自一个开关

### 1. 为什么要拆开

v46 做的是**一对**开关：取消勾选，「开始」和「停止」一起静音。用起来不够——这两个词的误触发性质完全不同：

- **「开始」**在中文日常说话里出现频率极高（「开始做…」「我们开始吧」「刚开始」），是最需要单独掐掉的那一个；
- **「停止」**一般是你**故意说**的（要光标停下来），多数人希望留着。

所以 v48 把它拆成两行独立勾选，位置就在**设置 → 语音控制 → 总开关词方案的下面**：

> ☑ 响应「开始」（开启光标移动）
> ☑ 响应「停止」（停止光标移动）

- 标签里的词**跟着你选的方案走**：选「开启 / 关闭」就显示「响应「开启」」「响应「关闭」」，选「打开 / 关闭」也一样——不用再猜「上方词对」指的是哪两个词。
- 只关一个，另一个照常工作；两个都关，等于以前那个总开关。
- **「移动 / 静止」「眨眼 / 闭眼」「张嘴 / 闭嘴」和三个声控按键永远不受影响**：即使把「开始」「停止」都关掉，光标移动仍然可以用「移动」「静止」开关。
- 改动**即时生效**，不需要重启软件，也不需要重开语音控制。

### 2. 旧配置怎么办

如果你在 v47 里把「总开关词」整对静音过，升级后**首次启动会自动把两个子开关都设为关**——不会因为拆开而突然又开始响应。你自己单独设置过的组合（比如只留「停止」）不会被改。

## v47：双音节词「左键 / 右键 / 中键」——单音节漏识别彻底解决

### 1. 单音节到底有多不稳

你反馈「1 和 2 不如 3 灵」，这次不再靠零散样本，而是把每个候选词放进真实的三槽配置里量：**两个 TTS 音色（晓晓女声 / 云扬男声）× 说话前静音 0 / 0.3 / 1 / 2 / 3 / 4 秒 × 每格 5 次 = 每词 60 次**，全部用真实的 KWS 模型离线跑。

| 词 | 命中 | 命中率 | 备注 |
|---|---|---|---|
| 左 (zuǒ) | 25/60 | 42% | 男声 30 次**一次都没中**（单关键词隔离测试同样 0/5，不是路径竞争） |
| 中 (zhōng) | 30/60 | 50% | 男声静音少于 1 秒时全不中 |
| 右 (yòu) | 40/60 | 67% | 静音 1 秒女声 0/5、男声静音 2 秒 0/5 |
| 三 (sān) | 45/60 | 75% | 三个单音节里最好的，仍有整段静音全灭 |
| 点 (diǎn) | 50/60 | 83% | |
| 后 (hòu) | 55/60 | 92% | |
| 下 / 前 / 上 | 60/60 | 100% | 强擦音起音，抗停顿 |
| **左键 / 右键 / 中键** | **180/180** | **100%** | 三词合计，男女声、0–4 秒静音全覆盖 |

两个关键结论：

1. **失手是「整段全灭」，不是概率降低**。同一个词、同一段音频，某个前导静音长度下 5 次全不中，换个长度 5 次全中——说明那一刻识别器根本没把这段声音当成这个词。用起来就是「有时候怎么念都没反应，过一会儿又好了」，比「偶尔漏一次」难用得多。
2. **单音节之间差得很大，但没一个能到 100%**。这也是为什么上一版换「左/右/中」有效却不彻底：只是从更差换到了没那么差。

**为什么单音节吃亏**：关键词的第一个音节没有左侧上下文，识别器只能靠这一小段声音决定「要不要开始匹配」；一个音节说完词就结束了，没有任何补救机会。**双音节等于给了第二次机会**——第一段没到阈值，第二段（「键」）还会继续加分，而且它有一个新的、干净的起音。

### 2. 默认值、候选词、自动升级

- 三个声控按键的默认词改为 **左键 / 右键 / 中键**，在下拉里带 **★** 标记（实测最优）。
- 候选词调整为 **左键 / 右键 / 中键 / 三 / 前 / 后 / 上 / 下 / 点**（9 个）。**去掉了单音节的「左」「右」「中」**：它们分别是双音节词的严格前缀，一旦两路同时启用，说「左键」可能连带触发「左」那一路。
- **已装 v46 的配置会自动升级**：首次启动把恰好是旧默认的「左 / 右 / 中」改写成「左键 / 右键 / 中键」并写回设置，**你自己选过的词（比如把 2 号换成「后」）不会被改动**；设置界面里显示的和实际识别的始终一致。

## v45：声控按键点按模式——听到即点击一下，不再要求持续念

### 1. 问题

实测反馈：一二三在实际使用中不太灵敏——是不是因为要求长按持续按键导致的？

**是。**按住（hold）模式的工作方式是：每识别到一次关键词就 (重新) 武装一个 0.8 秒的按住窗，持续发声时麦克风能量检测不断把窗口往后推。这意味着：

- **单发一个「一」**只按住约 0.8 秒——想做"点一下"还得等它自己松开；
- **拖长音「一——」**经常只命中一次甚至不命中（识别模型对持续元音的再检测很差），靠能量续窗撑着——开头那一下就可能漏；
- **识别边缘性**：单音节「一」本来就处于识别模型的边缘，之前的用法（连续念）掩盖了这一点，现在单独点按使用时就暴露了。

### 2. 点按模式

设置 → 语音控制 → 声控按键下方新增**「点按模式：听到即点击一下，而非按住」**（默认关闭，保持 v43/v44 的按住行为）：

- **开启后**：每听到一次关键词就立即短点一下——按下约 0.1 秒后松开，**不分析是否长按、不做能量续窗**；
- 单个「一」就是一次点击，反应更快，识别的边缘性影响大大降低（只需要命中一次，不需要持续命中）；
- 连念「一，一，一」就是连续多次点击；
- 切换模式时自动松开残留的按键，避免旧的按住窗穿越到新语义里。

两种模式随时可切：需要按住（比如按住 W 前进）用默认的按住模式；需要快速点按（比如单击、单步触发）就开点按模式。

## v44：声控按键独立通道——声控时不误触张嘴点击，感叹号可隐藏

### 1. 你报告的现象与真正的原因

报告的现象：声控按键与张嘴点击「共享一个触发条件」——关掉张嘴点击后声控按键好像失灵了，同时打开又容易在声控时误触张嘴。

排查结论（附实测证据）：

- **代码里两条通道是完全独立的**：声控按键走「语音识别 → 按住窗 → 分区注入」，张嘴点击走「嘴部手势 → 离合器 → 分区注入」，中间没有任何共享的门控。用真实识别器实测「张嘴点击关闭 + 声控按键开启」：说「一」照样按下/松开（v44 集成用例 8/8b 永久回归这条）。
- **"失灵"的观感来自两个默认绑定都是鼠标左键**：张嘴点击开着时，说「一」**必然张嘴**，张嘴手势直接触发左键——和声控按键按的是同一个键，看起来"声控按键在工作"；关掉张嘴点击后，声控按键识别不到（「一」是单音节，识别天然偏边缘，需要连续念），左键不按——看起来"失灵"了。识别的边缘性一直都在，之前被张嘴点击的动作掩盖了。**使用要领：持续念「一——」或「一，一，一，一」**，能量续窗会把按住窗一直往后推。
- **"声控时误触张嘴"是真的，这一版修了**：说「一」要张嘴，张嘴点击开着时就会同时触发。v44 起**声控按键按住期间张嘴点击自动被压制**（运行时压制，不写设置），说完松开立即恢复。两条通道同时开也不会叠加触发。

## v43：声控按键——说「一」按住一个键，持续发声就一直按着

「张嘴点击」要一直张着嘴，久了累。这一版加了另一种「按住」方式：**持续念「一……」就等于一直按住你绑定的键**，停下来就松开。

### 1. 怎么用

1. 设置 → **语音控制** → 勾选要用的「声控按键」（默认三个**全部关闭**，要用哪个开哪个）。
2. 每个槽位下面有一行按键绑定（留空 = 鼠标左键；录法与 v28 的张嘴点击按键相同，支持 Ctrl+C 这类多键序列）。
3. 对着麦克风**持续念「一……」**：按键立刻按下并保持；**停下来约 1 秒**自动松开。说「二」「三」同理。

| 槽位 | 触发词 | 默认按键 |
|---|---|---|
| 声控按键 1 | 「一」 | 鼠标左键 |
| 声控按键 2 | 「二」 | 鼠标左键 |
| 声控按键 3 | 「三」 | 鼠标左键 |

### 2. 「按住」是怎么实现的（两道保险）

单音节词「一」很短，识别器对**拖长的单音**命中并不可靠（实测：分离的「一，一，一，一」每次都中；一口气拖长只能命中一次甚至零次）。所以按住语义靠两个机制叠加：

- **命中按下（0.8 秒窗）**：每识别到一次「一」，按键按下并保持至少 0.8 秒；连续念时窗口不断被新的命中刷新。
- **能量续窗（声音不断，按键不松）**：只要麦克风还有声音（音量超过语音门限），每 100ms 把按住窗再推 350ms——**换气、拖长音、识别器暂时没吐词都无所谓**。保护上限：**最后一次命中之后最多再按 4 秒**，防止环境噪声把一次命中无限延长。
- **松开**：声音停止约 1 秒后自动松开，节奏与「张嘴点击」的闭嘴即松一致。

### 3. 行为细节

- **不受 3 秒同词冷却限制**：v42 把冷却改成同词 3 秒一次，但「按住 = 连说」本来就是预期行为——语音键的命中**豁免冷却**；开关词（移动/眨眼/张嘴…）的冷却照旧。
- **默认关闭（opt-in）**：「一」在中文日常语音里太常见（「一个」「一起」都带这个音），开启槽位后识别器会多监听这个词，**日常说话可能偶尔误触发按下**。所以三个槽位默认全关；不开启时识别器完全不听数字词，与 v42 零差别。设置行的说明里也写了这一条。
- **总开关联动**：语音控制总开关关闭时，所有声控按键立即松开并停止监听；更换开关词组时同样清空。
- **三路点击互不影响**：声控按键 / 张嘴点击 / 眨眼点击各自独立，随意组合；声控按键在游戏模式下也可用（走的是同一套分区注入通道）。
- **识别仍是完全离线**：同一套 5 MB 关键词模型，开启后最多多监听 3 个词。

## v42：说「闭嘴」「闭眼」关不掉点击——语音开关被旧点击模式「接管」了

### 1. 现象

想要的组合是「移动＋闭嘴」= **光标可以移动，但张嘴不会点击**；实际张嘴照样点击。把三个开关列成清单：

| 你说什么 | 管什么 | 应该的效果 |
|---|---|---|
| 「张嘴 / 闭嘴」 | 张嘴点击 | 开 = 张嘴出点击；关 = 张嘴没有任何动作 |
| 「眨眼 / 闭眼」 | 眨眼点击 | 同上，换成单眼闭合 |
| 「移动 / 静止」 | 光标移动 | 只停/只走光标，**不碰点击** |

三者应该互不影响、随意搭配——但「闭嘴」这一路根本关不干净。

### 2. 根因：软件里有两条点击路径，关掉一条还有一条

- **旧路径**：上面的「点击模式」下拉（悬停点击 / 眨眼点击 / 张嘴点击三种变体），手势直接换成**鼠标键**。
- **v28 并行路径**：「张嘴点击」「眨眼点击」**复选框**，手势换成**你绑定的按键序列**（默认也是左键）。两条路径本来就并存，复选框开启时会压制对应的旧模式，防止一个手势点两下。

问题出在 gestures.js 的接管设计：**复选框一关，对应的旧模式就自动顶上**（这是给「不想要按键路径、就想用经典模式」的人准备的）。于是：

- 复选框开着的人：说「闭嘴」→ 复选框关闭 → **旧「张嘴点击」模式接管** → 张嘴照样出左键；
- 复选框关着、用经典模式的人：说「张嘴」→ 复选框打开 → 切到按键路径（还在点）；说「闭嘴」→ 复选框关闭 → **又退回经典模式**（还在点）。

也就是说，无论哪种配置，「闭嘴」都表现为「没效果」——语音开关在两个都开着的路径之间来回切，从来没真正关掉过。

### 3. 修法：语音说关 = 两条路径全静音

新增一个**运行时压制标记**（不写入设置，重启即清）：

- 说 **「闭嘴」**：复选框照旧关闭（设置界面同步、立刻持久化），**同时压制旧点击模式路径**——张嘴彻底没有任何动作。就算复选框**本来就关着**（原来这种分支只弹一句「本就关着」），压制也会生效。
- 说 **「张嘴」**：解除压制并打开复选框——回到按键路径（默认左键）。
- **停止 → 重新开始**追踪时自动复位压制（和「静止」在重新开始时自动恢复移动是同一条规矩）：新会话永远从「全部按设置来」开始。
- 从没用过语音词的人**完全不受影响**：不传压制标记时 gestures.js 的行为与从前一字不差，经典模式照常。
- 「眨眼 / 闭眼」与旧「眨眼点击」模式的关系做了完全对称的处理。

### 4. 顺手修：连说两条指令，第二条被吞

原来的 3 秒冷却对**所有词**生效：说完「移动」紧接「闭嘴」，第二条会被静默丢弃（只有日志里一行 cooldown），恰好砸中「移动＋闭嘴」这种连说场景。现在**冷却只对同一个词生效**：不同词随时可以连说；同一个词 3 秒内仍只认一次（防一句话误触发连发）。

### 5. 顺手排查了其它组合

- **「静止」＋ 张嘴/眨眼点击**：v40 已修——「静止」只停光标移动，点击路径不经过它（本次复核通过）。
- **「移动」＋ 眨眼**：眨眼的手势报告与光标移动门控互不相干（复核通过）。
- **总开关词（开启/关闭/开始/停止）**：仍然是整体启停（相机 + 光标 + 点击全停），这是设计本意。
- **悬停点击（dwell）模式**：它不是张嘴/眨眼类手势，语音开关管不到它——如果你用的是悬停点击，请直接用「点击模式」下拉调整。
- 手动勾选/取消复选框的行为与从前一致：手动取消勾选会恢复经典模式（除非之前说过「闭嘴」——那个压制会持续到你说「张嘴」或重新开始追踪）。

### 6. 验证

- **28 项单元用例全部通过**：经典路径保留性（没说语音词时行为不变）、压制覆盖三种张嘴模式变体、眨眼对称用例（含非自主眨眼拒绝窗口）、复选框开启时 v28 路径归属、v40 语音路由回归、同词冷却、渲染器/主进程源码契约。
- **三个负向对照**全部变红：退回 gestures.js 的压制条件 → 6 项失败；退回同词冷却 → 失败；退回语音处理接线 → 失败。
- v40 / v41 检查页在新代码树上全部通过（check39 页面测的是 v40 有意替换掉的旧一次性回正行为，在 v41 基线上同样失败，与本次改动无关）。

## v41：校准完光标上下乱抖——增益公式量纲错了

### 1. 根因：一个把增益放大几千倍的单位错误

`computeComfortGain` 想回答的问题是「这段头部动作只走了 X 像素，要放大多少倍才能到角落」。它的两个输入是：

- **记录的位移**：每帧的 `deltaX/deltaY` 是**屏幕比例**（主循环就是这么用的：`mouseX += deltaX * screenWidth`），40 帧加起来大约是 `0.3`；
- **到角落的距离**：`targetDistance` 是**像素**，1080p 上是 `540`。

两个数直接相除：`540 / 0.3 = 1800`，再开方，得到 **×41**，被上限截成 **×12**。

> 也就是说：**只要 `sum` 小于 39.7（= 540 ÷ 12^1.05），结果就一定是 ×12**——而任何真实头部动作的 `sum` 都远小于这个数、又远大于 0。所以**每一次校准、每一个方向，写进去的都是整整 ×12**，测量数据完全没参与运算。

于是校准一结束，四个方向全是 ×12：摄像头那点看不见的抖动（增益 1 时约 0.05 像素/帧 → 几乎不动）被放大 12 倍，就变成光标每秒跑几百像素的乱晃。竖直方向最明显，因为上下两个方向的增益还可能不一样（一个 ×12、一个 ×1.3），同一份抖动往上推 12 份、往下只推 1.3 份——**净效果就是光标一直往上窜，你一拨回来它又窜上去，看起来就是「莫名其妙的上下抖动」**。验证按钮只有 110px 高，这个状态下点不中，校准自然次次失败。

同一个 bug 还让校准面板的进度条**永远停在 0%**（同样的相除），你可以回想一下是不是没见过它涨——这就是这条 bug 的旁证。

### 2. 修法：把两边换成同一单位

```js
const travelled = Math.abs(sum) * screenExtent;   // 屏幕比例 → 像素
const rawGain = (targetDistance / travelled) ** (1 / (1 + acceleration));
```

`screenExtent` 就是屏幕尺寸（`targets.x * 2`，因为 `targets` 是「中心到边」的距离）。进度条同样乘了回去。

实测（1280×720 视口，正常幅度的转头，40 帧 × 0.2 像素/帧）：

| | 修前 | 修后 |
| --- | --- | --- |
| 单步算出的增益 | **×12**（顶到上限） | **×1.43** |
| 四步走完写入的值 | 左 12 · 右 12 · 上 12 · 下 12 | 左 ×2.58 · 右 ×2.58 · 上 ×2.32 · 下 ×2.32 |
| 进度条 | 一直 0% | 38% |

### 3. 旧校准留下的 ×12 会被自动清掉

老版本的校准结果全是 12，那些数字里没有任何关于你的信息。补丁启动时会检查：**四个方向的增益都 ≥ 11.5 → 全部改回 1**（“未校准”状态）。所以你不用手动去点「重置」。

### 4. 防抖兜底（万一你的增益本来就该很大）

量纲修好后增益通常只有 1～3 倍，抖动问题基本就没了。但为了“再也不会抖到没法用”，又加了一层：

- **上限从 ×12 降到 ×6**，且**上下（左右）之间最多差 2 倍**（压缩时保持几何平均，整体手感不变）。两边差得越多，同一份抖动被「整流」成单向漂移就越厉害——这就是「自己往一边跑」的来源。
- **按实际增益自动加死区和平滑**：死区 ≈ 0.6px × (增益-1)，平滑系数 = 1/(1+0.35×(增益-1))。增益 1 时两者都是「什么都不做」，所以**没校准过的方向行为一点没变**。
- 死区只挡「小到不可能是你做的动作」的帧：×6 时约 3px/帧（≈110px/s），正常移动是 10px/帧以上，不会被吃掉。
- 新增设置 **光标移动 → 校准后的防抖**：关 / 标准（默认）/ 强。选「关」就是完全原始（限幅和对称化仍然保留，那两个才是防窜的主因）。

仿真（同一段零均值抖动，8 秒，1080p）：

| | 光标往返行程 |
| --- | --- |
| 修前（×12 / ×1.3，无滤镜） | **544px** |
| 只限幅 + 对称化（×3.95 / ×1.97） | 353px |
| 再加防抖（×2.32 / ×2.32，即修好后的真实增益） | **61px ≈ 9px/s** |

真实转头几乎不受影响：同样增益下，4 秒慢速转头的行程 418px → 410px（**-2%**）。

### 5. 校准本身的三处小修

1. **只统计朝目标方向的帧**：以前头晃回去的帧会把 `sum` 抵消掉，`sum` 越小算出的增益越大——正是抖动的放大器。
2. **验证阶段（10 秒门）从按钮左侧、与按钮同高处起步**：以前光标停在上一个方向结束的**屏幕角落**（贴边），残留抖动会让它沿着边上下跑，而那正是最难点中的状态。现在只剩一次**向右的水平移动**（按钮 380px 宽、110px 高，上下抖几十像素也还在按钮里）。
3. **验证门的文案**同步说明这一点（「光标已放到绿色按钮左侧、与按钮同高的位置」）。

### 6. 实测

- 校准纯逻辑 + 防抖 + 语音路由 + 源码契约 **98 项**全过。
- 校准流程（无头浏览器、mock 依赖）**16 项**全过：增益落在 0.8～4、上下/左右 ≤2 倍、进度条 38%、验证阶段光标在 (中心x-260, 中心y)。
- 回归：v40 的 35 项回正流程全过；v39 的感叹号用例与 v40 基线完全一致（15 项是 v40 主动改掉的旧行为）。
- 负向对照：把量纲退回旧写法 → 3 项挂（增益又变 12 / 全 6）；去掉限幅+防抖 → 契约 2 项挂。

## v40：回正顺序修正（先回正 → 再回中 → 再张嘴）+ 更短的回中间隔 + 「静止」只停移动

### 1. 校准失败的真正原因：回正的**顺序**错了

v39 的回正阶段是这样的：一点完「确认」，光标**立刻**被搬到屏幕中心，头姿零点**立刻**被重设成「当前姿势」——可这时候你的头还**仰在右上角**。

于是发生两件事，都指向同一个结果：

1. 被记成「正对中心」的那个姿势，其实是**仰着头的角上姿势**（零点从一开始就偏了）；
2. 你把头转回来的这一下，被算成一次**大幅度移动**，把光标从中心推了出去——所以下一方向根本**不是**从中心出发。

两次污染叠加，测出来的增益偏小，就是你看到的「调完只能动屏幕一小块」。

### 2. 现在：三段式，每一步都等你

| 阶段 | 面板说什么 | 你要做什么 | 光标 |
| --- | --- | --- | --- |
| ① 等待回正 | 「请先回正头部」 | 把头转回正前方 | **冻结**在刚才的位置，头怎么动都不跟 |
| ② 滑回中心 | 「光标正在回到中心…」 | 保持不动、放松 | 0.7 秒平滑滑到屏幕正中心 |
| ③ 等待确认 | 「光标已回到中心——现在张嘴」 | **张嘴** | 停在中心 |

- **先回正、再回中、再张嘴**，顺序就是这个。回正期间光标一动不动，所以「转回来」的那一下**推不动光标**。
- 头**停稳约 0.35 秒**就自动进入第 ② 段；如果你的头压根没动（说明本来就正着），**约两秒**后也会自动开始——面板上写的就是「大约两秒」。
- 想快一点：点 **「我已回正，把光标送回中心」** 或按 **空格**。
- 这一阶段**张嘴不算数**：会提示「请先把头回正」。因为刚测完方向时你正仰着头，张嘴就能确认的话，顺序又回到老问题上了。确认只在第 ③ 段生效。
- 头姿零点在**第 ② 段落地那一刻**才取——取的正是你此刻（已经回正）的姿势，所以「以此位置为基准向另一个角移动」是准的。
- 回正阶段仍然**不记录**任何位移（转回来那一下不算测量数据）。
- 小优化：光标本来就在中心附近（40px 内）时直接跳到第 ③ 段，不多问一次。

### 3. 自动回中：新增 0.5 秒 / 1 秒，默认改 2 秒

| 选项 | 说明 |
| --- | --- |
| 关闭 | 不自动回中 |
| **0.5 秒**（v40 新增） | 停一下就回中，偏移几乎随时被清零；适合短促移动、频繁瞄准 |
| **1 秒**（v40 新增） | 比 0.5 秒稳一点，仍然很勤 |
| **2 秒（v40 起默认）** | 原来的 3 秒偏慢，日常用这个更跟手 |
| 3 / 5 / 10 秒 | 保持原样 |

间隔越短回中越频繁，代价是「停住想一下」时会被拉回中间；觉得太勤就往上调。原有的保护都在：**任何点击、按住鼠标键、离合器 pin、校准进行中都会清零倒计时**，光标还在动就永不回中。

### 4. 「静止」只停光标移动，不再连点击一起关

以前说「静止」走的是和 **F9** 同一条路径：整个跟踪停掉（主进程 `enabled=false`），所以**点击也一起失效**——这不是这个词的意思。

现在「静止」只关**光标移动**这一半：

- 相机继续跑、跟踪状态不变，**第二 / 第三离合器照常**。所以 **「静止」→「张嘴」→ 点一下** 完全可行：光标停在按钮上，嘴一张就点下去。
- 说「移动」恢复移动；如果此时跟踪是**整体停着**的，「移动」会**顺带把它启动起来**（否则光标会一直是死的，没人知道为什么）。
- 模式键（默认 **F9**）：在「静止」状态下按一下 = **恢复移动**，再按一下才真正停止。
- 方案词 **「开启 / 关闭」**（或「开始 / 停止」「打开 / 关闭」）仍然是**整体开关**，行为一点没变——那是总闸。
- 点「启动」按钮也会清除「静止」状态。

技术上的实现：语音命令现在带 `source` 字段区分是**方案词**还是**功能词**；渲染器把命令交给一个纯函数决定要做什么（`voice-command.js`，可单测），「静止」不再经过 `toggle-tracking`；主循环里给光标累加加了一道 `cursorMovementOff` 闸门，自动回中也会被它挡住（不会偷偷把光标挪走）。

### 5. 实测（本机验证）

- 回正流程（无头浏览器，mock 依赖）**35 项**断言全过：回正开始时光标**不动**、头在动时也**不动**、提前张嘴被拒绝、停稳后自动起滑、落位精确落在中心、落位才取零点、按钮/空格强制推进、已在中心时直接进确认、Esc 取消。
- 回正纯状态机（calibration-recenter.js）**20 项** + 自动回中（含 0.5 / 1 秒）**8 项** + 语音路由（静止/移动/开启/关闭/眨眼/张嘴）**16 项** + 源码契约 **7 项** = **56 项**全过。
- 真机识别链路（stub Electron + 真实 sherpa-onnx WASM + TTS 音频）**11 项**全过：「静止」→ `off/movement/source=movement`；静止后 **点击仍然被允许**（嘴部手势照样到达 helper、`click` IPC 没被拒）；「关闭」→ `source=scheme`；「移动」重新接合主离合器。
- 负向对照（测试有牙齿）：把回正改回「立刻置中」挂 **20 项**；去掉语音 `source` 区分挂 **7 项**；去掉光标移动门控挂 **2 项**。

## v39：静止自动回中 + 校准「回正头部」+ 感叹号大小可调

### 1. 为什么光标用着用着会偏左/偏右

直接移动模式是**相对**的：光标位置＝历次头部移动的累加。摄像机的细微漂移、坐姿变化、脸部特征点的抖动，全都会加进这个累加值里。十几分钟后，「头正对屏幕」对应的光标位置已经不在中间了——于是你总觉得光标偏在一边，想调回来又得使劲转头。

v29 的「开启时回中」只在**每次开始移动**时清一次，软件常开的话基本用不上。v39 把它变成**周期性**的：

### 2. 静止 N 秒自动回到中心位置（光标移动栏）

| 选项 | 说明 |
| --- | --- |
| 关闭 | 不自动回中（旧行为） |
| 2 / 3（默认）/ 5 / 10 秒 | 光标连续这么多秒**完全没动、也没有点击**，就平滑滑回所在屏幕的中心 |

- 回中是**滑动**（0.6 秒缓动），不是瞬移，不会被误认为卡顿或跳帧。
- 到达中心后，**当前头部姿势就被当作新的「正对中心」**（头部倾斜模式的零点同时校准）。
- **点击受保护**：任何点击（含眨眼/张嘴点击）、按住鼠标键、离合器 pin、校准进行中，都会把倒计时清零；光标只要还在动，永远不回中。也就是说「瞄准按钮 → 停住 → 点击」不会被打断。
- 仅「直接移动」模式生效（摇杆模式本身就会回中）。

### 3. 校准：每一步都先「请回正头部」

以前四步是连着测的：朝左上转完，头常常还偏着，下一步的测量里就混进了「转回来」的反向位移，算出来的增益偏小——**于是校准完光标只能动到屏幕一小块**。

现在每一步之前都插一段**回正阶段**：

1. 光标**先被放回屏幕正中心**，屏幕中央显示一个绿色圆点（此刻的光标就在这里）；
2. 提示 **「请回正头部」**：把头转回自然正对屏幕的姿势，这个姿势就是新的「正中」；
3. **张嘴确认**（或点「开始下一方向（张嘴）」/ 空格）→ 开始测这个方向。

回正阶段**不记录**任何头部动作（转回来的那一下不算数）。第一个方向之前也有这一段，所以每一步都是「从屏幕中心出发 → 朝角落转」，四个方向的增益才可比。

### 4. 黄色感叹号可调大小

v38 的一秒感叹号偏大，现在有下拉：**大**（v38 原始 68×90）/ **中**（小一号，默认）/ **小**（小两号）/ **特小**（小三号）。位置、1 秒时长、渐隐、跟随光标的行为都不变，只是整体按比例缩放（描边宽度也跟着缩，不会糊）。

### 5. 基础手感：最大速度默认值提高

「最大移动速度」默认从 1200 px/s 提到 **2400 px/s**。原因是校准增益会给灵敏度乘上系数，1200 的上限让**有意的**转头动作都要一秒多才能横穿屏幕，手感发滞。2400 仍然能压住抖动尖峰（抖动是几十毫秒的爆发，被限速削平），但正常移动不再被拖慢。觉得还慢，可以在「点跟踪」里继续往上调（最高 6000）。

### 6. 实测（本机验证）

- 自动回中纯状态机（auto-recenter.js）**19 项**用例全过：关闭直通、静止计时、移动/点击清零、满 N 秒起滑、滑动中被打断、完成吸附 + 重置头姿零点、目标未知/已在中心附近不起滑、设置中途关闭立即取消。
- 校准流程 **40 项**断言全过（无头浏览器，mock 依赖）：start 直接进回正、每次回正都把光标置中、回正期间记录的帧被丢弃、四步之间各回正一次（共 4 次）、第四步后直接进验证门、验证门点中央按钮成功、空格可确认回正、Esc 可取消。
- 感叹号尺寸 12 项断言：默认 medium 49×65、large 68×90、small 34×45、tiny 23×31，偏移随尺寸缩放，来回切换不残留。
- 回归：v38 的语音/离合器联动主进程集成 **16/16** 仍全过；v38 的感叹号 HUD 用例（显式指定 large）全过。
- 负向对照：摘掉回正阶段挂 **15 项**，摘掉尺寸缩放挂 **7 项**，摘掉自动回中挂 **8 项**（测试有牙齿）。

## v38：语音指令联动离合器 + 光标旁「黄色感叹号」回执

### 1. 问题：语音开关和离合器是两道独立的门

v36 的语音开关只翻设置里的复选框，而点击类功能还要过离合器这一关：**说「张嘴」打开了「张嘴点击」，但第二离合器没接合时照样点不了**——必须先按住（或切到）第二离合器键。语音说的和按键管的对不上，说话等于白说。

### 2. 现在：说出来的话就是离合器

每条被识别的语音指令在翻转开关的同时，也**直接驱动对应的离合器**：

| 语音词 | 开关 | 离合器动作 |
| --- | --- | --- |
| 「移动」/ 各方案的开启词（开启、开始、打开） | 光标移动 | **接合**主离合器（无需按键即可移动） |
| 「静止」/ 各方案的关闭词（关闭、停止） | 光标移动 | **分离**主离合器 |
| 「眨眼」 | 眨眼点击 | **接合**第三离合器 |
| 「闭眼」 | 眨眼点击 | **分离**第三离合器 |
| 「张嘴」 | 张嘴点击 | **接合**第二离合器 |
| 「闭嘴」 | 张嘴点击 | **分离**第二离合器 |

- 只在对应离合器**本身在设置里开启**时才会联动（离合器关着时它的门本来就是常开的，语音不去动它）。
- **硬件永远优先**：之后任何时候碰一下那个实体离合器键（按下或松开都算），语音覆盖立即清除，控制权交还按键——语音永远压不住你亲手按的键。
- 关闭「语音控制」总开关、或重新设置离合器键/模式时，所有语音覆盖一并清空。

### 3. 黄色感叹号：每次识别成功的回执

软件最小化时看不见界面里的提示，很难确定「刚才那句听到没有」。现在**每次语音识别成功**（包括总开关词和所有开关词），**光标右上角会出现一个黄色感叹号，停留 1 秒**（结束前 0.25 秒渐隐）：

- 画在**屏幕遮罩层**上、跟随**真实光标**位置，所以**软件最小化、甚至光标不在任何窗口里时都能看到**。
- 和张嘴/眨眼点击的指示条一样不影响点击；追踪开关关闭时照样显示（说的「开启」就是让你确认的）。
- 黄色笔画带深色描边，浅色/深色背景下都看得清（不是细字形的“!”：竖笔和点都画得粗，余光也抓得到）。

### 4. 实测（本机验证）

- 主进程 harness（真实 WASM + KWS 模型 + TTS 语音）16 项单元用例 + 16 项集成用例全部通过：「张嘴」→ 第二离合器接合并下发 `zone H:mouth 1`、「闭嘴」→ 分离、「眨眼/闭眼」→ 第三离合器同理、「移动/静止」→ 主离合器接合/分离（moveMouse 放行/挡住）、实体键边沿清除语音覆盖、关闭语音控制清空全部覆盖、每条指令后遮罩层数据携带 1 秒的 `voiceIndicatorUntil`。
- 遮罩层 HUD 无头浏览器 15 项断言通过：感叹号出现/定位/1 秒后隐藏/边缘钳制/渐隐/跟随光标。

## v37：限速 + 张嘴确认 + 10 秒验证门（校准不再有「调完更糟」）

v35 的校准把「舒适转头幅度」放大到能走到屏幕角落，副作用是**同样的倍率也放大了小抖动**：头部一点细微晃动，光标就飞快窜出去。v37 从三处收口。

### 1. 最大移动速度（限速）

设置 → 光标移动 → 点跟踪 → **最大移动速度**（默认 **1200 像素/秒**，可调 300–6000）。

- 做法是**「提高灵敏度 + 限制速度」组合**：校准照样放大方向灵敏度（所以舒适幅度仍能走到角落），但每帧的位移被速度上限钳住——**稳定的转头动作照样累加到角落，抖动爆发却只能慢速滑动**。
- 上限按**每秒像素**算，60Hz 下 1200 px/s ≈ 每帧 20 px；掉帧时按时间折算，不会因为卡顿一下跳很远。
- 只在**「直接移动」**模式下生效（摇杆类模式有自己的一套速度逻辑）。觉得正常移动太慢就把这个值调高。

### 2. 校准入口搬到「开始」按钮旁边

主界面顶部大 **「开始 (F9)」** 右边就是绿色的 **「校准舒适范围」** 按钮，**默认可见**——不用翻设置也能看到、随时能用（设置里原来那个按钮也保留）。未开始跟踪时点它会提示「请先开始头部跟踪（按「开始」）」。

### 3. 全程「张嘴」确认，自动准备

- 校准开始时会**临时打开「张嘴点击」**（结束后自动恢复你原来的设置），所以即便你平时没开这个开关，也能用嘴确认；如果它本来就开着，**不会多此一举去关它**。
- 每一步的确认从**按空格**改成**张开嘴**（按钮文字也改成「确认（张嘴）」）；空格、R、Esc 仍然保留，作为键盘备用。
- 界面上大字号提示当前是第几步、朝哪个角、以及「到达舒适极限后张嘴确认」，进度条显示本动作等效的距离百分比。

### 4. 10 秒验证门：点不中就当没校准

四步确认完，**新灵敏度立刻临时生效**，同时在屏幕正中央出现一个巨大的绿色按钮 **「调试完成（剩 N 秒）」**：

- 你需要在 **10 秒内用头控鼠标把光标移到这个按钮上并点它**——光标在按钮上时**张嘴**（或你平时的点击方式）就算点中。
- 点中 → 校准结果**正式保存**并显示四个方向的倍率。
- **超时没点中 → 本次结果直接作废**，灵敏度**恢复成校准前的状态**，并给出「重试校准 / 退出」两个选项。这就是为了杜绝「本来能用，调完反而用不了还卡死改不回去」——只要你调完连中央按钮都够不到，系统就替你回滚。
- 验证门期间按 **Esc** 取消，同样回滚。

> 小提示：如果经常在验证门超时，说明某一步转得**太狠**（倍率被算得过大），重试时把那个方向的动作收小一点再张嘴确认。

### 5. 实测

- 限速纯函数 6 条断言（正/负方向、Y 轴换算、掉帧折算、dt 上限）全过；负向对照去掉钳制后 5 条立刻失败。
- 校准流程 31 条断言：张嘴确认四步、验证门倒计时、点中提交、超时回滚、Esc 回滚、张嘴点击临时开启/恢复（含「本来就开着不重复翻转」）、无移动时确认被拒——负向对照分别去掉回滚（挂 2 条）与去掉张嘴确认（挂 10 条）。
- 主界面按钮与限速滑杆的真实接线（按钮紧邻开始按钮、默认 1200、未开始跟踪时的提示）4 条断言通过。
- v36 / v34 / v33 旧回归套件（14 + 12 + 127 条）全过。

## v36：语音开关（移动/静止、眨眼/闭眼、张嘴/闭嘴）+ 标题标注内存

v34 给了语音一个**总开关**（光标移动开/关）。这一版把「按嘴开关」补全：光标移动之外，**眨眼点击**和**张嘴点击**也能各用一对词开关，且每个开关可以单独不监听。

### 1. 三组新词

| 语音开关（设置 → 语音控制） | 打开说 | 关闭说 | 作用 |
|---|---|---|---|
| 「移动 / 静止」 | 移动 | 静止 | 光标移动**开 / 关**（和上面选的开关词是同一个总开关，两套说法都有效） |
| 「眨眼 / 闭眼」 | 眨眼 | 闭眼 | **眨眼点击**复选框 开 / 关 |
| 「张嘴 / 闭嘴」 | 张嘴 | 闭嘴 | **张嘴点击**复选框 开 / 关 |

- 三行开关**默认全部勾选**，语音控制一开就都在听；取消勾选的那一行就不再监听（例如你只想要「眨眼/闭眼」，就把另外两行关掉，识别器会按新词表重建，约 1 秒）。
- 语音控制总开关关掉时，这三行是灰的（不可点）——没开语音，监听无从谈起。
- 「语音控制」这个**大标题后面直接写着「（开启后内存消耗增加）」**，不用翻说明也知道代价。

### 2. 行为细节

- **都是「开/关」，不是「切换」**：说「闭眼」就是把眨眼点击设为关；已经关着再说一次，只会弹一句「本就关着」，不会反过来打开（和 v34 的总开关一致）。开着再说「眨眼」同理。
- **改的是同一个复选框**：语音开关和设置里那个「眨眼点击 / 张嘴点击」勾选框是**同一个状态**，也会立刻持久化——语音关掉后，下次启动仍然是关的；打开设置窗口，那个勾也是同步的。（v42 起语音说「关」还会同时压制旧的点击模式路径——见「v42」一节。）
- **3 秒冷却**：v42 起只对**同一个词**生效，不同词可以连着说（「移动」→「闭嘴」不再被吞）；同一个词 3 秒内仍只认一次。
- **注意第三/第二离合**：「眨眼」只负责把「眨眼点击」这个**复选框**打开；如果你还启用了**第三离合器**（v28），眨眼点击本身仍要第三离合接通才真正生效。「张嘴」与第二离合同理。这正好是有用的组合：离合当安全锁，语音当总闸。
- **只监听启用的词**：三个开关全开时共 8 个词（开关词 2 + 6），全部本地离线识别，不上传音频。

### 3. 实测与调参（为什么识别阈值变了）

- 加了 6 个词后，识别器的**束搜索路数**必须从 2 提到 **8**：路数太少时「闭嘴」这种与「闭眼」「张嘴」共享音节的词会被直接剪掉——离线测试里路数 8 以下、阈值 0.25 时它**一次都不命中**（这不是麦克风问题，是解码器没给它留位置）。
- 阈值从 0.25 放宽到 **0.20**：4 个 TTS 音色 × 8 个词 = **32/32 全部命中**；19 条无关语音/易混淆句零误触发，只有「闭嘴吧，先听我说」这类**句子里真的含关键词**的句子会触发（符合关键词识别的本意）。
- 内存：8 条路径比 2 条更吃内存，实测主进程 **加载后约 +150 MB、识别过几轮后稳定在 +190 MB 左右**（关闭语音控制仍需重启才释放）——所以标题上直接标了内存提示。
- 负向对照：把「移动/静止」的指令映射改回旧的「只认方案词」写法，主进程测试立刻挂 2 条；把渲染端的复选框切换逻辑短路，UI 测试挂 8 条——说明这些断言确实在测东西。

## v35：舒适范围校准（够不到角落时按自己的范围重设灵敏度）

### 1. 为什么够不到角落

这个软件的光标是**相对移动**的：头部动多少，光标就动多少（乘灵敏度、过加速度曲线）。所以「怎么都到不了左上角」不是映射边界的问题，而是**你朝那个方向能舒服转动的幅度，产生的光标位移不够走完半屏**。每个人的脖子活动范围、坐姿、摄像头位置都不同，所以统一调「灵敏度滑杆」总是顾此失彼（调高了别的方向又太冲）。

### 2. 校准怎么用

1. 先按 **开始**（F9）让头部跟迹跑起来——没开始跟踪时点校准会提示先开始。
2. 设置 → **光标移动** → 点 **校准舒适范围…**
3. 屏幕出现四个角落方块，按提示依次做 4 步：

| 步骤 | 高亮的角落 | 你要做的 |
|---|---|---|
| 1 | 左上 | 朝左上转，转到「再转就难受」的位置 |
| 2 | 左下 | 同上，朝左下 |
| 3 | 右上 | 同上，朝右上 |
| 4 | 右下 | 同上，朝右下 |

每一步：朝高亮方向转 → **觉得到极限了按空格**（或点「确认」）。**不需要真的碰到角落方块**，方块只是告诉你方向。面板上有实时进度条，显示「这个动作相当于从屏幕中央到角落距离的百分之多少」，到 100% 就表示同样的动作正好能走到角落（不到也没关系，校准会按比例补足）。

4. 四步完成后显示四个方向的倍率（如 `左 ×2.30 · 右 ×1.85 · 上 ×3.10 · 下 ×1.60`），立即生效并保存。

**快捷键**：空格 = 确认本步，R = 重做本步，Esc = 取消。

### 3. 它到底改了什么

- 只改**方向灵敏度倍率**（`headTrackingGainLeft/Right/Up/Down`，默认 1），不推翻你原有的水平/垂直灵敏度与加速度——是在它们基础上乘一个系数。
- 每步的算法：把这一步记录到的每帧头部移动，按**当前灵敏度与加速度曲线**逐帧模拟出光标位移，再解出「让这个位移正好等于屏幕中央→角落距离」所需的倍率（因为加速度是幂函数，这个解是闭式的，不是瞎猜）。四个方向各测两次（左上/左下都给「左」），取平均。
- **只在「直接」移动模式生效**；摇杆类模式（4/8 方向）不受影响，否则不对称的倍率会把摇杆方向带歪。
- 单步记录不足 10 帧、或几乎没有移动时会被拒绝并提示重做，防止误按空格把倍率拉满。
- 倍率钳制在 **0.5×–12×**，再夸张的动作也只会到这个范围。

### 4. 什么时候要重做

坐了别的椅子、换了摄像头位置/角度、把笔记本立起来——凡是你「舒适极中位」变了的，重新校一次就行。想回到未校准：设置 → 光标移动 → **重置舒适范围校准**（倍率全回 1）。

### 5. 实测（本机验证）

- 闭式解数值验证：随机帧序列下 `增益^(1+加速度) × 原始位移` 与目标距离误差 **< 1%**。
- 方向性：小幅度动作的方向得到大倍率、大幅度动作的方向倍率小（测试里 12 vs 11.79 vs 2.30，符号关系符合预期）。
- 覆盖层流程 4 步推进、快捷键、太少帧拒绝、完成面板倍率显示、持久化链路全部有断言。
- 负向对照两条（把增益函数改成恒返回 1；去掉键盘监听）分别导致 5 条 / 11 条断言失败——说明测试真在测东西。

### 6. 为什么不做「绝对映射」（把光标位置绑到头部位置）

因为那会和这个软件现有的整套设计冲突：绝对映射下头部必须一直在某个位置，回到中位光标就跳回中间，点击/拖拽/离合/摇杆全部要改写，而且用户已经习惯相对移动的手感。校准只是把「相对移动的比例」按你的身体量一次，风险小得多。

## v34：语音控制（说「开启」开始移动，说「关闭」停止）

给一个「不用动手」的总开关：**开口说一个词，光标就跟随头部开始移动；再说一个词，立刻停下**。代替「闭眼保持几秒」那种要屏住呼吸的操作，也不用去够 F9。

### 1. 怎么用

1. 设置 → **语音控制** → 勾选 **语音控制**。
2. 下面「开关词」选一组（默认第一组）：

| 开关词 | 打开用 | 关闭用 |
|---|---|---|
| 说「开启」开 / 「关闭」关（默认） | 开启 | 关闭 |
| 说「开始」开 / 「停止」关 | 开始 | 停止 |
| 说「打开」开 / 「关闭」关 | 打开 | 关闭 |

3. 对着麦克风正常说一声：屏幕左下角会弹一个提示（如「语音：光标移动已开启」），开始/停止按钮同步变成对应状态。

第一次勾选后识别器需要 **约 1 秒**加载模型（在后台线程排队执行，设置窗口不会卡住）；这段时间说的话会被忽略，稍等半秒再说即可。

### 2. 行为细节（都是刻意这样设计的）

- **是「开/关」，不是「切换」**：说「关闭」就是把光标移动设为关闭；当前已经是关闭状态时再说「关闭」不会有任何副作用（不会像 F9 那样又给打开）。
- **只监听你选的那两个词**：换词组后，另一组词立刻失效（模型按词组重建），不会出现「两种词都能用」的混乱。
- **3 秒冷却**：v42 起只对**同一个词**生效，不同词可以连着说（「移动」→「闭嘴」不再被吞）；同一个词 3 秒内仍只认一次。**v43 起声控按键（「一/二/三」）豁免冷却**——按住语义本来就要连说，见「v43」一节。
- **和 F9 / 开始按钮完全等价**：走的是同一个开关，光标回到屏幕中心、离合状态重置、虚拟手柄摇杆归零等行为完全一致。
- **提示浮层**：每次真正生效都会在左下角显示 2.5 秒，确认「它听懂了」。
- **麦克风只在勾选时使用**：取消勾选会立刻释放麦克风（`track.stop()` + 关闭 AudioContext），不在后台偷听。

### 3. 为什么是「离线关键词」而不是语音助手

- 不联网：没有网络延迟、不依赖任何云服务（国内也不需要翻墙），断网、飞行模式照用。
- 不上传音频：模型只做「这两个词的发音匹配」，不是语音转文字，识别完就丢，不保存、不上传。
- 硬盘占用小：int8 模型约 5 MB（+ 16 MB WASM 运行时）；只在你勾选「语音控制」时才加载。
- 内存是有代价的：实测主进程 **RSS 增加约 125 MB（加载时）、用一段时间后约 200 MB**（WASM 运行时 + 模型）。**关闭后不会立刻回收，要重启软件才释放**——内存吃紧的机器建议不需要时关掉再重启。**v36 起监听词更多（最多 8 个），实测增幅约 +150 MB（加载）/ +190 MB（稳定），标题上也直接标注了这一点。**

### 4. 打包进补丁的东西

| 新增文件 | 大小 | 作用 |
|---|---|---|
| `resources/app/node_modules/sherpa-onnx/` | 16 MB | 纯 WASM 的语音运行时（无原生 DLL，不存在 ABI 兼容问题） |
| `resources/app/node_modules/tracky-mouse/vendor/kws/` | 4.9 MB | int8 中文关键词模型三件套 + tokens |
| `resources/app/src/electron-main/voice-control.js` | — | 主进程识别逻辑（词组、冷却、加载/销毁） |

卸载脚本会把它们一并删掉（它们都记在安装清单里）。

### 5. 实测数据（本机验证，不是估计）

- 5 个词（开启 / 关闭 / 开始 / 停止 / 打开）合成语音：**5/5 全部命中**。
- 音量降到 0.3 倍：仍能识别。
- 40 ms 小块流式喂入（模拟真实麦克风回调）：正常命中。
- 模型自带的其他唤醒词语音、纯静音、白噪声：**零误触发**。

### 6. 已知限制

- 环境嘈杂、离麦克风太远（>1 米）或说得含糊时会漏识别；把词说得短促清晰些最稳。
- 只支持上表三组词。想换成别的词需要改 `voice-control.js` 里的 `WORD_TOKENS`（每个字的拼音带声调写法，需与 `tokens.txt` 里的 token 对应）。
- 说话时如果正在放音乐/视频，建议戴耳机或调低音量，避免自己的声音被当成关键词（3 秒冷却能挡掉大部分连发）。

## v31：游戏模式默认关闭（不再弹出手柄）+ 头部触控板归入游戏模式

### 1. 以前为什么会"一进去就弹手柄"、退出电脑还卡

虚拟手柄是由一个后台小程序（`tracky-vigem-stick.exe`）通过 ViGEmBus 创建的。它的老行为是：**一被启动就创建虚拟 Xbox 360 手柄**。于是：

- 每次打开 Tracky Mouse，Windows 都会枚举到一个新控制器（右下角提示"正在设置设备"）；
- 关掉软件（或者关机）时，这个虚拟手柄被移除，**Windows 要重新扫描一遍设备列表**——这就是退出时卡上一会儿的原因。

而只要你开过「头部 → 右摇杆」「Joy-Con 桥接」「Joy-To-Key」「头部触控板」里的任意一项，后台小程序就会在启动时被拉起来，于是每次都会弹手柄。

### 2. v31 的做法：默认不创建手柄

| 状态 | 后台程序 | 虚拟手柄 |
|---|---|---|
| **启动时（游戏模式默认关闭）** | 仅在开了「眨眼点击 / 张嘴点击」时运行，**不带虚拟手柄** | **不创建** |
| 按 **F10** 打开游戏模式 | 重启为"带手柄"模式 | 创建（这时才会出现在系统里） |
| 再按 **F10** 关闭游戏模式 | 立刻重启为"无手柄"模式 | **立即移除**（不等退出软件） |
| 只有头部触控板、且游戏模式关闭 | **完全不会启动** | 不创建 |

要点：

- **游戏模式每次启动都是关的**，不记忆上次状态。这样你永远不会在"只是开机想用光标"的时候莫名多出一个手柄。
- 关掉游戏模式时，手柄是**当场消失**，而不是等你退出软件才消失——退出软件时系统已经没东西可移除，启动/关机都不再卡。
- 鼠标模式的**眨眼点击 / 张嘴点击**仍然需要后台程序注入按键，所以它会继续运行，但**不创建虚拟手柄**（内部用 `--no-pad --no-joycon` 启动，连 ViGEmClient.dll 都不加载）。
- 设置里的**「手柄自检」**仍然可用：它会临时创建手柄扫一遍摇杆，测完就销毁。

### 3. 头部触控板归入游戏模式

「头部 → 触碰按键（摄像头感应板）」这一组设置从**鼠标模式**移到了**游戏模式**：

- 在设置页切到"游戏模式"标签才能看到它；
- **只有游戏模式开启时，感应板才会按下按键**；关闭游戏模式会立刻清空感应板表，并释放还按着的键（不会卡键）；
- 感应板的位置、大小、按键、双方案、互斥切换等全部照旧，只是归属变了。

> 如果你用的是「眨眼点击 / 张嘴点击」，它们仍在**鼠标模式**的「点击」分组里，和游戏模式无关，关掉游戏模式照样能用。

### 4. 需要知道的

- 从 v30 升上来，设置全部沿用，不用重配。
- ViGEmBus 驱动现在**只有用游戏模式时才需要**：只用光标和眨眼/张嘴点击的话，不装驱动也不影响。
- 如果你希望开机就用摇杆，按一下 F10 即可（也可以把游戏模式开关改成一个更顺手的键）。

## v29：开启光标移动时，光标回到屏幕正中心

**问题**：每次开启光标移动（点「启动」或按 F9），光标会跳到屏幕左下角的一块。

**原因**（三个叠在一起）：

1. 旧代码把光标放到「**所有显示器拼起来的总矩形**」的中心。多屏时这个点根本不在你的主屏中间——副屏在左边/下边时，那个点正好落在主屏的左下角一带。
2. 上一次运行残留的**离合位移**（`clutchOffset`）没有清掉，开启的第一帧会把它再叠加一次，把光标整体推偏，甚至顶到屏幕边缘。
3. 头部倾斜（3D）模式下光标位置是**绝对**的（按头的俯仰/偏摆换算），零点不校准就会被拉向某个角落。

**现在的行为**：

| 行为 | 说明 |
|---|---|
| 回到**光标所在那块屏幕**的正中心 | 不是所有屏幕拼起来的总中心。副屏上的光标就在副屏居中。 |
| 以**当时的头部位置**作为中心点 | 头跟踪是相对位移，所以头不动 ⇒ 光标就停在正中心；倾斜模式同一时刻重新校准零点，同样回到正中。 |
| 清掉残留离合位移 | 开启瞬间重置位移，不会把光标整体推偏。 |
| 顺带把「重新居中」算作非手动接管 | 否则跳到中心那一下会被误判成「你动了鼠标」，导致开头两秒不跟头。 |
| 相对鼠标模式（游戏）只对齐原点、不瞬移光标 | 那种模式靠相对位移驱动视角，绝对定位会打断游戏。 |
| 设置项「**开启时光标回到屏幕中心**」 | 设置 →「光标移动」第一项，**默认开启**。取消勾选则保持光标在原地、从当前位置继续跟着头走。 |

> 注意：如果你把**主离合器**开着（按住键才移动），开启跟踪的瞬间光标会被离合器钉在原地，等你按住离合键开始移动时它才会从「刚才那块屏幕的中心」出发——这是离合器的设计（不该乱动光标），不是没生效。

## v27：桌面摇杆映射（摇杆方向 = 按住某个键）

参照 Steam「桌面布局」做的摇杆→键鼠映射，核心是**按住语义**：

| 动作 | 行为 |
|---|---|
| 摇杆推过门槛（约半行程） | 绑定的按键**按下并保持**——系统自动重复触发，网页/文档持续滚动 |
| 摇杆回到中心 | 按键立刻**松开**，不会像以前那样「回中又触发一下」 |
| 保持偏移（如一直低头） | 键一直被按住 → 一直滚动/一直触发 |

这就解决了你反馈的问题：以前是「低头触发一次、头回正又触发一次」的边沿式输出；现在是**保持低头 = 键被持续按住**。绑定 ↑/↓ 或滚轮上/下后，**抬头网页就连续向上滚、低头就连续向下滚**。

**两处可绑定**：

1. **头控右摇杆**（设置 → 头部 → 摇杆 分组新增 4 个下拉）：头向上/向下/向左/向右分别绑定一个动作，选项有无、**滚轮上滚/下滚**、↑↓←→、PgUp/PgDn、空格、回车、鼠标左/右/中/X1/X2 键。其他键可以在设置文件里手写 `vk:0xNN`。
2. **Joy-Con / Pro 摇杆**（Joy-To-Key 映射表）：每行的「按键」下拉新增**摇杆 ↑↓←→**（Pro 手柄分左/右摇杆共 8 个方向），目标键可以是任意键、鼠标键或 v26 的多键序列。摇杆推过去 = 整串键按住。

**一个共用离合器**（设置 → 头部 → 摇杆 分组）：

- 模式三选一：**始终**（默认，无需按键）、**按住**、**切换**；按住/切换需绑定离合键。
- 离合断开的瞬间，所有被摇杆按住的键**立即全部松开**，不会卡键；普通按键映射（Joy-To-Key 的按钮部分）不受离合影响。
- 触发门槛约半行程，带滞回：推过约 50% 才触发，退回约 35% 以内才松开，边缘抖动不会让键乱闪。只有**主导轴**生效，斜推只算一个方向。

## v21：白屏修复（v19/v20 打开只有空窗口）

现象：装完 v19 或 v20 后打开 Tracky Mouse，窗口在、标题栏和菜单栏（文件 / 编辑 / 查看 / 窗口 / Help）都在，但下面**什么都没有**——没有开始按钮、没有摄像头画面、没有设置面板，只有一片背景色。

原因不是主进程，也不是摄像头或硬件，而是**安装时漏了一个新文件**：

1. v19 把「头部触碰按键」写成了独立模块 `node_modules/tracky-mouse/src/touch-zones.js`。
2. 入口 `tracky-mouse.js` 用**静态 `import`** 引它——ES 模块是整体加载的，任何一个 import 找不到文件，**整个模块图直接失败**，`TrackyMouse.init()` 根本不会执行，于是渲染进程一个字都没画出来。
3. 而 `install.ps1` 复制文件用的是一份**手写的文件清单**，v19 新增这个文件时清单没跟着加，所以它**从来没有被装进去**。菜单栏由另一个脚本（`custom-menu-bar.js`）提供，不受影响——这正是"有菜单、没界面"的原因。

v21 三层修复，从根上断掉这一类问题：

| 修复 | 做法 |
|---|---|
| **不再依赖新增文件** | 把触碰区模块**内联进 `tracky-mouse.js`**，删掉独立文件。补丁从此只**覆盖已存在的文件**，不新增任何模块，安装器不可能再"漏"掉它 |
| **安装器不再手写清单** | `install.ps1` 改成**递归枚举 `patch\resources` 下的全部文件**，patch 里有什么就装什么。以后再加文件也不会漏 |
| **安装后自检** | 装完逐一检查渲染端所有**相对 import 是否都能找到目标文件**；只要有一个找不到，安装器直接报错中止，把"白屏"变成"安装失败"，不会留下一个打不开的应用 |

顺带：`install.ps1` / `uninstall.ps1` 会把 v19/v20 可能残留的 `touch-zones.js` 清掉。

**如果你已经装过 v19/v20**：直接再运行一次 v21 的 `install/install.ps1` 即可，不需要卸载、不需要重装 Tracky Mouse。安装器会先恢复原始文件再覆盖，设置不受影响。

## v20：桥接「看起来没反应」的修复 + 右摇杆垂直反向


### 1. Joy-Con → 虚拟手柄桥接静默失效

现象：老版本（v13 及更早）里 Joy-Con 一连上就能驱动虚拟手柄，Steam 控制器测试里能看到输入；升上来之后即使 Joy-Con 在按，虚拟手柄也没反应。

原因：v18 恢复桥接时把它改成了**必须手动勾选「Joy-Con → 手柄（桥接）」**，而老用户的设置里没有这项（默认关闭），升级后桥接就静默处于关闭状态——看起来像「桥接坏了」，其实是开关没开。此外还有一种静默失效：桥接离合模式选了「按住/切换」但**没设按键**，这时桥接永远无法接通，界面却没有任何提示。

v20 三处修复：

- **老设置自动迁移**：设置文件还带着 v13 痕迹（旧桥接离合开关，或已有 Joy-To-Key 映射——v13 里这两类用户桥接都是直接可用的）时，启动自动打开新桥接开关（一次性，之后你手动关掉不会再被打开）。
- **无键离合兜底**：桥接离合是「按住/切换」但没设按键时，视同「始终」，不再静默失效。
- **状态可观察**：桥接每次接通/断开都会写进 `%APPDATA%\tracky-mouse\tracky-vigem-stick.log`（`[app] bridge ENGAGED / disengaged`），helper 收到时也会记 `Joy-Con -> pad bridge enabled=true`——两条都在，桥接链路就从「黑盒」变成了可查的。

**升级后请确认**：设置 →「Joy-Con / 手柄按键」→「Joy-Con → 手柄（桥接）」应为勾选状态；然后按一下手柄上的任意键，Steam 控制器测试里虚拟手柄应有输入。

### 2. 右摇杆垂直反向（头往下 = 摇杆往上）

设置 →「头部 → 摇杆」新增**「右摇杆垂直反向（头往下 = 摇杆往上）」**开关（默认关闭），与原有的水平反向（「右摇杆反向」）并排。适合游戏视角俯仰方向和习惯相反（inverted-Y）的情况。只影响右摇杆。

## v19：头部触碰按键（摄像头感应板）

原来的「头部 → 左摇杆」是模拟量：头偏多少摇杆偏多少，游戏里的角色走得又飘又难控制——摇杆是连续的，而走位需要的其实是「按住 W 就往前走」这种**开关量**。v19 把左摇杆整个换成了一套新逻辑，原理类似跳舞机：

> 在摄像头画面中间放几块**感应板**。头部（追踪的鼻子位置）碰到某块板，这块板绑定的键就被**按住**；头离开，键就**松开**。斜着头同时压两块板，两个键就一起按住。

**编辑方式（全在摄像头画面上）**：设置 →「头部 → 触碰按键」→ 勾选开关 → 点「编辑触碰区」（或摄像头画面右上角的同名按钮）进入编辑模式：

- **空白处拖拽**：画一块新感应板（单击空白处 = 放一块默认大小的板）
- **板内拖拽**：移动；**拖角**：缩放（最小 2%）
- **双击板**：按顺序按下一串键（如按住 Ctrl 再点 C），**全部松开**约半秒后录成 `Ctrl + C`（v26 起支持多键；Esc 取消）
- **Enter**：选中板后手动输入按键序列（如 `ctrl+c`，v26 新增）
- **Delete / Backspace**：删除选中的板；**Esc**：取消选择
- **左上角「方案 1 / 方案 2」按钮**：切换当前编辑的方案（v22）；编辑只作用于当前方案，另一方案的板以虚线显示作参照
- 每个方案最多 8 块板；位置大小以画面比例存储，换分辨率不跑位
- 画面上实时显示状态：头在板里时板变绿、键名亮起（方案一蓝、方案二紫）

**离合器与其它功能一样**：「始终」（默认，头一碰就触发）/「按住」/「切换」三档，可绑任意鼠标键、键盘键或手柄键。v22 起方案一、方案二各有独立的一组离合设置。总开关（F9）关闭或离合断开时，所有按住的键立即释放，不会卡键。

底层实现：渲染端每帧用鼻子位置命中测试 → 主进程门控（总开关 + 离合）→ helper（tracky-vigem-stick.exe）注入键盘/鼠标。只支持键盘与鼠标键；与右摇杆、桥接、Joy-To-Key 互相独立、可同时使用。旧的 `headStickLeft*` 设置会在启动时自动清理。

## v18.1：右手柄 SL/SR 搞反了

按键映射里，按 Joy-Con（R）上示意图标着 SL 的实体按键，程序却识别成 SR——因为任天堂的报告文档里这两个位的命名跟随横握方向，而右手柄相对左手柄是**镜像**的，程序按文档位序直译就反了。现在 helper 对 Joy-Con（R）单独交换 SL/SR 的解读，与示意图和实体按键一致；Pro 手柄（没有实体 SL/SR）不受影响。只重新编译了 `tracky-vigem-stick.exe`，其余文件与 v18 完全相同。

## v18：Joy-Con 投射虚拟手柄回来了

v14 为了给头部→摇杆腾地方，把「Joy-Con → 虚拟手柄」整条链路和它的离合器删了。实际用下来它还是不可替代——有些游戏只认手柄输入，Joy-To-Key 顶不上。v18 把它加回来，并且和头部→摇杆**共存**：

**接管规则（关键设计）**

> 桥接开启时，**只有手柄真的在被使用**（按键按下、扳机、或摇杆推过约 8% 的死区）才接管虚拟手柄；手柄一松手，头部追踪立刻继续驱动摇杆。

这样「始终」模式既不占着摇杆不放，也不会出现「开了桥接就再也用不了头部控摇杆」的问题。

**映射表**

| Joy-Con / Pro | 虚拟 Xbox 360 |
|---|---|
| A / B / X / Y | A / B / X / Y |
| L / R（肩键） | LB / RB |
| ZL / ZR | LT / RT（扳机，数字量 0 或 255） |
| 方向键（含 Joy-Con L 的 ▲▼◀▶） | 十字键 |
| Minus / Plus | Back / Start |
| 摇杆按下（LStick / RStick） | LS / RS |
| Home | Guide |
| Joy-Con L 摇杆 | 左摇杆 |
| Joy-Con R 摇杆 | 右摇杆 |
| Pro 手柄 | 左右摇杆都驱动 |
| SL / SR / Capture | 无对应（忽略） |

单只 Joy-Con 的摇杆方向跟随**「Joy-Con 握持方向」设置**（v23）：默认**直立 / 握把**（竖着握或装在充电握把上，推上就是上）；选**横握**时自动旋转 90° 匹配单手横握（旧行为）。方向键的旋转与摇杆一致。Joy-Con 停在蓝牙默认的 simple HID 模式时也有 8 方向档位可用。

**离合器**：「Joy-Con → 手柄（桥接）」分组里，模式可选 `始终` / `按住` / `切换`，默认**始终**（碰手柄就接管，不用按键）。选 `按住`/`切换` 后可以指定任意鼠标键、键盘键或手柄键。

## v17 修的是什么事

现象：**Joy-Con 按键映射（Joy-To-Key）绑好之后完全没反应。**

这是一个真正的 bug，而且是三层叠加，任何一层都足以让整张映射表失效：

**1. 映射表每一行都被跳过（根因）**

映射行存的是 `hidR:a` 这种写法，而 helper 内部标识手柄的字段是裸的 `R` / `L` / `P`。比较时没有去掉 `hid` 前缀，`"hidR" != "R"`，于是**每一行在第一道判断就被跳过**——日志里明明有 `N key mapping(s) active`，按键却永远不会触发。v17 修正了比较逻辑，`hidR:a` 与 `R:a` 两种写法都认。

**2. Joy-Con 停在「简单模式」时被误判为掉线**

蓝牙连接的 Joy-Con 默认发送 11 字节的 simple HID 报告（`0x3F`）。helper 原本把「读到少于 12 字节」当成设备断开处理，于是健康的手柄被反复踢掉、重连，按键自然读不到。另外，切到标准模式（`0x30`）用的输出报告少了必须的 8 字节 rumble 数据，Joy-Con 会直接忽略，所以模式切换其实从来没成功过。

现在：断开判定改为「读取失败或少于 3 字节」；切模式的输出报告补齐为规范的 11 字节（rumble 8 字节 + 子命令 `0x03` + 模式 `0x30`）。

**3. 没装 ViGEmBus 时，按键映射也被连累**

helper 以前在 ViGEm 连接失败时直接退出。但按键映射根本不需要虚拟手柄。现在它会**降级为「纯 Joy-To-Key 模式」继续运行**：只有摇杆投射依赖 ViGEmBus，按键映射不受影响。

**顺手把绑定方式改顺手了**

映射表每行前面新增 **「按手柄键选择」** 按钮：点一下，再按 Joy-Con / Pro 手柄上的那个键，就选好了；点 **「+ 添加映射」** 会直接进入等待按键状态，按完自动新增一行。两个下拉框仍然保留，需要手动选、或键位名跟实物对不上时还能用。

## v16 修的是什么事

现象：**Steam 的控制器设置里能看到虚拟手柄的摇杆在动，但进游戏就没反应。**

这几乎不是「没有输出」，而是**游戏没有把这个手柄当成它在读的那一个**。v16 针对三种真实原因分别做了处理：

**1. 手柄「从没动过」→ 游戏/Steam 忽略它**

游戏和 Steam 输入都按「最后有动作的手柄」来选设备。刚创建、一直静止的虚拟手柄很容易不被选中。现在虚拟手柄会：

- 在创建后轻推两下摇杆（左右各 80ms，幅度约 37%）；
- 每次**切换前台窗口**（比如切进游戏）时再轻推一次，因为那正是游戏重新枚举手柄的时刻。

这个轻推**只在摇杆本来没有输出时**才做，绝不会覆盖你正在操作的真实值；也可以在设置里关掉（「轻推摇杆，让游戏认到虚拟手柄」）。

**2. 手柄不在「玩家 1」槽位 → 游戏只读槽 0**

如果同时还有别的手柄（真实 Xbox 手柄、被 Steam 虚拟化的 Joy-Con 等）占着 XInput 槽 0，我们的手柄会是槽 1，很多游戏只读槽 0 就完全没反应。现在 helper 启动会把槽位写进日志：

```
virtual pad is XInput user index 0 (most games read index 0)
```

看到 `index 1` / `2` / `3` 就说明被别的手柄占了——先断开其它手柄再试。

**3. 无法判断到底哪一环坏了 → 加了一键自检**

「头部 → 摇杆」分组底部有 **「测试虚拟手柄（15 秒）」** 按钮：临时接管虚拟手柄，让两根摇杆画 15 秒圈，同时提示你打开 <https://hardwaretester.com/gamepad> 观察。

- 浏览器里摇杆会转、游戏里不转 → 问题在游戏/Steam 侧（见下面「游戏里没反应」排查表）。
- 浏览器里都不转 → 驱动或 DLL 的问题，看日志。

**另外**：helper 的 stderr 现在会落盘到 `%APPDATA%\tracky-mouse\tracky-vigem-stick.log`（超过 512KB 自动轮换成 `.log.1`），打包版没有控制台也能查。

## v15 修的是什么事

v14 把「虚拟手柄右摇杆」从「鼠标输出模式」里拆出来、放进新的「头部 → 摇杆」分组，并且**默认模式是「按住」**（要按住手柄 LB/RB 才动）。结果是：以前只要勾一个选项就能用的头部控视角，升上来之后**勾了开关也不动**，看起来就像功能被删了。

v15 的修正：

- **新增「始终（不需按键）」模式，并设为默认**。这就是加离合器之前虚拟摇杆的用法——勾上「右摇杆」开关，头一动视角就动，一个键都不用按。
- 想用离合键的人，把模式改成 `按住` 或 `切换` 即可（离合键默认手柄 LB / RB，可自定义任意键）。
- **旧设置自动迁移**：以前选过「虚拟手柄右摇杆」的用户，升级后自动变成「右摇杆开关 = 开 + 模式 = 始终」；v14 里模式还是「按住」但离合键仍是默认值（说明没自己配过）的，也自动改成「始终」。
- 「鼠标输出模式」的说明里增加了指向「头部 → 摇杆」分组的一句话，避免再找不到。
- 顺手改了个手感问题：**手动动鼠标不再让摇杆归零**（以前会短暂打断视角），现在只有 F9 暂停追踪才归中。

## 安装

1. 把整个 `tracky-clutch` 文件夹解压到任意位置。
2. **退出 Tracky Mouse**（托盘/窗口里关掉）。
3. PowerShell 执行：

```powershell
powershell -ExecutionPolicy Bypass -File install.ps1
```

- 脚本会自动扫描 `%LOCALAPPDATA%\tracky-mouse\app-*` 打补丁，原文件备份在 `resources\.lmb-clutch-backup`。
- **装过旧版？直接跑即可**，脚本自动清理旧文件再打新补丁。
- **正卡在 v19/v20 白屏？** 直接跑这个安装器就好，不用卸载 Tracky Mouse，装完窗口内容就回来了。安装器最后会打印 `Renderer imports verified (15 modules).`——看到这行说明渲染端完整，不会再白屏。

## 必装：ViGEmBus 驱动（用摇杆投射才需要）

虚拟手柄需要一个内核级总线驱动，补丁无法自动安装，请手动装一次（所有虚拟手柄软件都靠它，安全可信）：

1. 下载：<https://github.com/nefarius/ViGEmBus/releases/latest>
2. 运行 `ViGEmBus_Setup_x64_installer.exe` 一路下一步。
3. 装好后设备管理器里会出现「ViGEm Bus Device」。

`ViGEmClient.dll` 补丁包已附带，无需另下。只用桌面/键鼠映射的话不装也能正常用。

**v31 起**：游戏模式默认关闭、也不会创建虚拟手柄，所以「只用光标 + 眨眼/张嘴点击」的人**不需要装这个驱动**；只有要用摇杆 / Joy-Con 桥接时才装。

| ↳ **开关方式 / 开关按键** | 「按住」= 按住期间点击生效；「切换」= 每按一下开/关。默认键：鼠标 X2（前进键）。 |
| **交换鼠标按钮** | 左右键互换（系统层面键位反了时用）。 |

> **声控按键（v43）**不在这个分组里，在 **设置 → 语音控制** 分组下：三个默认关闭的「声控按键一/二/三」开关 + 各自的按键绑定，持续念「一……」= 一直按住绑定的键、停下自动松开，详见「v43」一节。

### 头部 → 摇杆（Head → Analog Sticks）

| 设置 | 说明 |
|---|---|
| **右摇杆（头部 → 右摇杆）** | 开关：头动驱动虚拟手柄右摇杆（3D 游戏视角）。v19 起左摇杆由「头部 → 触碰按键」取代；v31 起那一组在**游戏模式**标签下，且游戏模式关闭时不触发。 |
| **右摇杆离合器模式** | `始终`（默认）/ `按住` / `切换`。区别见该行感叹号。 |
| **右摇杆离合键** | 默认手柄 RB。模式为「始终」时灰显不用。 |
| **右摇杆反向** | 开启后「头往右 = 摇杆往左」。只影响右摇杆水平轴。 |
| **摇杆死区** | 0–40%，默认 8%。圆形死区，头部小幅晃动时摇杆保持归中。 |
| **轻推摇杆，让游戏认到虚拟手柄** | 默认开。手柄创建时、切换前台窗口时轻推两下摇杆，让游戏/Steam 选中它；摇杆正在输出时不会触发。 |
| **测试虚拟手柄（15 秒）** | 让两根摇杆画 15 秒圈，配合 <https://hardwaretester.com/gamepad> 判断是「手柄本身」还是「游戏不读」的问题。 |

**三种模式的行为**：

| 模式 | 行为 |
|---|---|
| `始终` | 开关一勾，摇杆全程跟随头部，**不用按任何键**（旧版「虚拟手柄右摇杆」就是这个效果）。 |
| `按住` | 按住该摇杆的离合键时才跟随头部，松开立刻归中。 |
| `切换` | 按一下开、再按一下关；两个摇杆的开关互相独立。 |

- 摇杆只受其离合键控制，不受光标离合器影响。
- **F9 暂停追踪**时两根摇杆归中；**手动移动鼠标**不再打断摇杆。
- **桌面摇杆映射（v27）**：同一分组里还有「桌面模式：摇杆方向按住即按键」开关、共用离合器（模式 + 按键）、以及 4 个「头向上/下/左/右 →」下拉（滚轮上滚/下滚、方向键、PgUp/PgDn、空格、回车、鼠标键等）。**保持低头 = 所选键持续触发，头回正 = 松开**；低头绑 ↓ 或滚轮下滚、抬头绑 ↑ 或滚轮上滚，就可以用头滚动网页。详见「v27」一节。

**推荐配置（3D 游戏，最省事）**：

1. 装 ViGEmBus。
2. 勾上「右摇杆」开关 → 模式保持「始终」→ 进游戏，头一动视角就动。
3. 想只在需要时才控视角，把模式改成「按住」并绑手柄 RB（或键盘某键）。
4. 想让头部控制人物移动（WASD 类），改用「头部 → 触碰按键」（v31 起在**游戏模式**标签下，同样需要游戏模式开着）——比模拟摇杆顺手得多。

### Joy-Con → 虚拟手柄（桥接）

1. 装 ViGEmBus（和摇杆投射同一个驱动）。
2. 勾「Joy-Con → gamepad（桥接）」→ 离合模式保持「始终」。
3. 手柄连上后直接推摇杆/按键——虚拟 Xbox 360 手柄会同步出输入；松开手柄，头部立刻继续控摇杆。
4. 想只在按住某键时才允许手柄接管，把模式改成「按住」，再点「Bridge clutch key」按下任意键。
5. 和上面的 Joy-To-Key 可同时开：一个走手柄输入，一个走键盘鼠标输入。

- 桥接与 Joy-To-Key **互不影响**，同一按键可以既映射键盘又进虚拟手柄（不想要的话去掉其中一个即可）。
- 手柄**闲置时不占摇杆**：这是 v18 的核心取舍，避免「开了桥接，头部控摇杆就废了」。
- 只支持 **Joy-Con (L/R) / Pro 手柄**（走 HID）；其它手柄不会被桥接。

### Joy-Con / 手柄按键（Joy-To-Key）
- 「Joy-Con 按键 → 键盘/鼠标」开关 + 下方映射表。**绑定方式：点行首「按手柄键选择」→ 按 Joy-Con / Pro 手柄上那个键 → 点目标键按钮，按顺序按下一串键（如按住 Ctrl 再点 C），全部松开约半秒后录成 `Ctrl + C`（v26 起支持多键）**。点「+ 添加映射」同样会直接等你按手柄键，按完自动新增一行。
- **摇杆方向也能绑（v27）**：行的「按键」下拉新增**摇杆 ↑↓←→**（Pro 手柄分左/右摇杆）。摇杆推过约半行程 = 目标键按住不放，回中 = 松开；也受桌面映射离合器（在「头部 → 摇杆」分组）的门控。
- **手动输入按键序列（v26）**：点行内的 ✎ 按钮（或右键点目标键按钮），直接输入 `ctrl+c`、`shift+f5` 这类写法。
- 两个下拉框（手柄 / 按键）保留：手动改选、或某行想换成另一个键时可以直接下拉。
- 顶部有 Joy-Con 左右手柄示意图，鼠标移到某一行映射上会高亮对应物理按键；按手柄键捕获成功后也会高亮。
- 按住 Joy-Con 按键期间映射键保持按住，松开同步松开。
- 只支持 **Joy-Con (L/R) / Pro 手柄的原始按键**（走 Windows HID）。捕获到其它手柄（XInput / DirectInput 类）时会提示——那类手柄请用 Steam 或厂商驱动映射成键盘，或者只把它们当摇杆离合键用。
- 总开关默认关闭，映射表灰显时先打开上面的开关。
- **不需要 ViGEmBus**：只做按键映射时，即使虚拟手柄不可用，映射也照常工作。

## 游戏里没反应？按这个顺序查

「Steam 控制器测试里摇杆会动、游戏里没反应」是最常见的一类问题，几乎都不是补丁坏了，而是**游戏没把手柄当成它在读的那一个**。按顺序过一遍，一般三步内能定位：

| # | 检查 | 怎么做 / 说明 |
|---|---|---|
| 1 | **先确认手柄本身是好的** | 设置里点「测试虚拟手柄（15 秒）」，浏览器打开 <https://hardwaretester.com/gamepad>。两根摇杆会画圈 → 手柄没问题，问题在游戏侧；不画圈 → 驱动/DLL 问题，看日志。 |
| 2 | **看手柄的 XInput 槽位** | 打开 `%APPDATA%\tracky-mouse\tracky-vigem-stick.log`，找 `virtual pad is XInput user index N`。**N 必须是 0**；是 1/2/3 说明被别的手柄占了（真实 Xbox 手柄、Steam 虚拟化的 Joy-Con 等），先断开其它手柄。 |
| 3 | **Steam 输入怎么设** | 现代游戏（认 XInput）：Steam → 设置 → 控制器 → **关闭「Xbox 配置支持」**，让游戏直读 XInput。<br>只支持 DirectInput 的老游戏：反过来**保持 Steam 输入开启**，并且**通过 Steam 启动游戏**，让 Steam 把我们的 XInput 手柄转成它的虚拟手柄。 |
| 4 | **游戏自己的输入设置** | 很多游戏要在设置里把手柄选上，或**先按一下手柄按键**才会从键鼠切到手柄输入。我们的轻推脉冲会自动做这件事，但只在摇杆空闲时触发——若你进游戏时头一直在动，可以手动按一下手柄键。 |
| 5 | **反作弊** | Easy Anti-Cheat / BattlEye / Vanguard 等会屏蔽 ViGEm 虚拟手柄（这是它们的既有行为），这类游戏基本无解，除非游戏支持真实手柄直通。 |
| 6 | **显示模式** | 少数游戏在「独占全屏」下读不到新插入的手柄，改成「无边框窗口」再试；或者先开游戏再启动补丁（反过来也行，都试一次）。 |
| 7 | **确认这次真的用了新 exe** | 应用自动更新会还原补丁，重跑 `install.ps1`；日志开头应该有 `virtual Xbox 360 pad ready` 和槽位那行。 |

### 按键映射（Joy-To-Key）不生效怎么查

| # | 检查 | 说明 |
|---|---|---|
| 1 | 总开关 | 「Joy-Con 按键 → 键盘/鼠标」是否勾上；未勾时映射表是灰的，helper 也不会加载映射。 |
| 2 | 目标键 | 每行右侧的「目标键」不能为空（显示「设置键…」就是没设）。 |
| 3 | 手柄有没有被读到 | `%APPDATA%\tracky-mouse\tracky-vigem-stick.log` 里应有 `R connected, mode ...` / `L connected, mode ...`。没有就检查 Joy-Con 是否已配对、是否被 Steam 独占。 |
| 4 | 映射有没有加载 | 日志里应有 `N key mapping(s) active`，N ≥ 1。 |
| 5 | 按键事件有没有进来 | 按手柄键时日志应出现 `R: a` 这样的行（表示读到了按下）。有这行但目标键没反应 → 目标键被别的程序占用，换个键试。 |
| 6 | 是否老版本 | v17 之前映射表 100% 不生效（kind 比较 bug），先确认补丁版本。 |

### Joy-Con 桥接没反应怎么查（v20 起可全程用日志定位）

| # | 检查 | 说明 |
|---|---|---|
| 1 | 桥接开关 | 设置 →「Joy-Con / 手柄按键」→「Joy-Con → 手柄（桥接）」要**勾选**（v13 老用户升级到 v20 会被自动勾上）。 |
| 2 | 离合模式 | 「始终」最省事。「按住/切换」需要设离合键；**没设按键时 v20 起视同「始终」**，不再静默失效。 |
| 3 | 应用侧日志 | `%APPDATA%\tracky-mouse\tracky-vigem-stick.log` 应有 `[app] bridge ENGAGED`。没有 → 开关没开或 helper 没启动（看 `helper started`）。 |
| 4 | helper 侧日志 | 同一文件里应紧跟 `Joy-Con -> pad bridge enabled=true`。有这条但 Steam 里仍无输入 → 按一下手柄键，日志应出现 `R: a` 之类的按键行；有按键行但没输入 → 看「游戏里没反应」通用排查表。 |

## 已知限制（重要）

- **摇杆投射需要 ViGEmBus**：未装驱动时摇杆与桥接都无效（日志会提示），游戏里可能出现一个一直连着的「Xbox 360 手柄」。**按键映射不受影响**。
- **桥接时手柄优先**：桥接开启且手柄正在使用时，虚拟手柄由手柄驱动，头部摇杆暂时让位；松手后自动交回头部。这是设计行为，不是失效。
- **Joy-To-Key 只认任天堂原始按键**：Joy-Con (L/R) 与 Pro 手柄走 HID，能读到；XInput / DirectInput 类手柄（Xbox、PS、国产 2.4G 等）不能被映射成键盘——请用 Steam / 厂商软件做键位映射，或只把它们用作摇杆离合键。
- **Joy-Con 处于 simple HID 模式时键位名可能对不上**：helper 会尝试切到标准模式（v17 修正了切换包），若你的手柄始终停在简单模式、且某几个键名字不符，先用「按手柄键选择」按实物键绑一遍——捕获到的是实际能读到的那个键，比按名字猜可靠。
- **摇杆输出不随光标离合**：两根摇杆只受各自离合设置控制，主光标离合器不管它们；F9 暂停追踪会把两根摇杆归中。
- **游戏内灵敏度**：头动到屏幕边缘 = 摇杆推满，具体手感还要在游戏里再调；死区滑块可以先解决「自己乱抖」。
- **右摇杆方向相反**：水平方向用「右摇杆反向」，垂直方向用「右摇杆垂直反向（头往下 = 摇杆往上）」（v20 新增）。
- **离合键不会被拦截**：本补丁只读状态，不吞按键。
- **winmm 手柄的语义名（A/B/…）不做保证**：用捕获到的「按钮 N」即可。
- **应用自动更新会覆盖补丁**：重跑 `install.ps1` 即可。
- **未在真实 Windows 机器上运行验证**：JS 语法/静态检查、Go `go vet` 与交叉编译、设置界面无头渲染均已验证，实际手感需要你本机确认。
- 两个 exe 无代码签名，个别杀毒软件可能提示；源码在 `tools/` 里可自行编译。
